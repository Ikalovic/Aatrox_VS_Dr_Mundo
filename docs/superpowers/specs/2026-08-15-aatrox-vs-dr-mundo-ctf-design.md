# Aatrox VS Dr. Mundo CTF 设计文档

## 1. 目标

制作一道面向中等难度校赛的源码开放型 Web CTF 题。题目使用 Docker 单实例部署，以《英雄联盟》海克斯大乱斗为背景，提供简化的肉鸽闯关、回合制战斗、装备商店与海克斯抽取流程。玩家操控剑魔，依次击败小兵、野怪和英雄，最终击败 Boss 蒙多后由服务端直接返回 Flag。

主解必须依次利用：

1. SQL 注入查询海克斯数据库并选择隐藏海克斯“暗裔契约”；
2. 条件竞争重复领取精英战奖励，刷取金币和海克斯刷新券；
3. 批量购买的计价与落库不一致，重复装备并叠加高额属性；
4. 使用强化后的剑魔 Q3 将蒙多压入斩杀线，在蒙多大招回复前完成斩杀。

题目重点是条件竞争与业务逻辑漏洞。SQL 注入是必要利用链的一环，但采用直观的 UNION 查询，避免成为盲注题。

## 2. 非目标

- 不制作复杂美术、动画、音效或实时操作系统；所有图片位置保留为空白占位。
- 不完整复刻《英雄联盟》的全部装备、英雄技能或版本数值；基础面板属性只有生命、攻击和护甲，伤害不区分物理、魔法或真实类型。吸血、回复、减伤和斩杀可以作为技能或装备效果存在。
- 不提供多用户共享实例、注册系统、管理员后台或排行榜。
- 不依赖外部网络、Redis、消息队列或多个容器。
- 不将非预期 RCE、任意文件读取或容器逃逸设计为解题方式。

## 3. 交付形态

- 技术栈：Python 3.12、Flask、SQLite、原生 HTML/CSS/JavaScript、pytest。
- 部署：单个 Docker 容器，默认暴露 `8080` 端口；`docker compose up --build` 可直接启动。
- 实例模型：每队独立实例、独立 SQLite 数据库、独立会话与独立 Flag。
- 源码附件：选手得到完整业务源码、数据库初始化代码、Dockerfile 和依赖清单，但不包含真实 Flag。
- Flag：由环境变量 `FLAG` 注入；本地默认值为 `flag{development_only}`。只有服务端确认蒙多死亡后才读取并返回。

## 4. 玩家流程

1. 玩家进入首页并创建一局游戏，角色固定为剑魔。
2. 地图按“小兵战 → 野怪战 → 英雄战 → 商店/海克斯 → 精英战 → Boss”推进。
3. 普通战斗提供少量金币，用于让正常流程看起来完整，但正常总奖励不足以形成通关构筑。
4. 海克斯页面默认随机展示三个公开海克斯，支持名称搜索和使用刷新券重抽。
5. 玩家从源码发现搜索接口存在 SQL 注入，通过 UNION 查询枚举隐藏海克斯并选择“暗裔契约”。
6. 玩家从源码发现精英奖励的“检查—发奖—标记”不是原子操作，并发调用领取接口，重复获得金币与刷新券。
7. 玩家调用批量购买接口，利用去重计价、逐项落库的差异重复购买唯一装备；战斗引擎会累加库存中的每一行装备属性。
8. 玩家携带暗裔契约和重复装备进入 Boss 战，使用 Q1 → Q2 → Q3，在第三段触发最大生命值伤害和残血斩杀。
9. 蒙多死亡后，胜利接口在响应 JSON 中返回 Flag。

## 5. 页面设计

页面采用暗色卡片式布局；本期需要的图片资源先使用占位，后续由出题方补充：

- 首页：题目名、剑魔文字卡、开始游戏按钮。
- 地图页：纵向节点列表，显示已完成、当前和锁定节点。
- 战斗页：双方生命、攻击、护甲、回合日志和技能按钮。
- 商店页：金币、库存、装备列表、单买、批量购买和属性锻造器入口。
- 海克斯页：刷新券、随机三选一、名称搜索框和选择按钮。
- 胜利页：蒙多被击败的文字结果与 Flag。

前端只负责展示和发送动作，金币、库存、战斗状态、胜负与 Flag 均由服务端计算。开发者工具或直接调用 API 是预期解题方式。

## 6. 内容与数值

### 6.1 剑魔

剑魔基础属性：

- 最大生命：`7,000`
- 攻击力：`350`
- 护甲：`80`
- 初始金币：`1,200`
- 初始刷新券：`1`

技能采用简化回合制规则：

- 普攻：造成 `1.0 × AD` 伤害。
- 被动·赐死剑气：每三次主动攻击触发，追加目标当前生命 `5%` 的伤害，并回复同等实际伤害的 `50%`。
- Q1：原始伤害 `200 + 1.5 × AD`。
- Q2：原始伤害 `350 + 2.2 × AD`。
- Q3：必须在连续使用 Q1、Q2 后释放，原始伤害 `600 + 4.0 × AD`。
- E·暗影冲决：本回合调整站位，并使剑魔本回合造成伤害的 `30%` 回复为生命，不造成独立伤害。
- R·大灭：持续三回合，攻击力提升 `25%`，每场战斗只能使用一次。

所有普通攻击、技能伤害和基于生命值的额外伤害都使用同一个护甲减免公式：

`实际伤害 = floor(原始伤害 × 100 / (100 + 目标护甲))`

### 6.2 蒙多

蒙多固定属性：

- 最大生命：`32,000`
- 初始攻击力：`5,000`
- 护甲：`200`
- 大招阈值：当前生命低于最大生命的 `40%`，即低于 `12,800`
- 大招效果：攻击力提升到 `8,000`，此后每个蒙多回合结束回复最大生命的 `40%`，即 `12,800`，回复不超过最大生命

蒙多的普通攻击使用与剑魔技能相同的护甲减免公式。剑魔基础 80 护甲会把蒙多觉醒前的单次攻击从 5,000 降为 2,777；预期重复装备构筑拥有 29,000 最大生命，足以承受 Q1、Q2 之后的两次攻击并进入 Q3 回合。

回合顺序固定为：玩家动作结算 → 暗裔契约斩杀判定 → 蒙多低血大招判定 → 蒙多攻击 → 蒙多回复。此顺序保证暗裔契约可在蒙多回复前完成斩杀。

### 6.3 暗裔契约

“暗裔契约”是隐藏棱彩海克斯：

- 抽取权重为 `1`，海克斯总权重为 `1,000,000,000`，单次正常概率严格为 `0.0000001%`。
- 只有 Q3 享受强化。
- Q3 的技能原始伤害乘以 `7.5`。
- Q3 在上述技能伤害之外，再增加目标最大生命 `35%` 的原始伤害；对蒙多为 `11,200`。两部分相加后统一经过护甲减免。
- Q3 全部伤害结算后，如果目标生命大于 `0` 且小于最大生命的 `40%`，立即斩杀。

没有暗裔契约时，重复装备只能提高常规伤害，无法稳定越过蒙多的高护甲与每回合回复；没有重复装备时，暗裔契约的 Q3 也不足以把满血蒙多压进斩杀线。

### 6.4 核心装备

装备方向参考 ARAMKit 的剑魔海克斯大乱斗构筑数据，重点采用“心之钢 + 狂徒铠甲 + 霸王血铠”的生命值与生命转攻击路线；数值为题目专用，不复刻线上版本：

| 装备 | 价格 | 攻击力 | 最大生命 | 护甲 | 特殊效果 | 限制组 |
|---|---:|---:|---:|---:|---|---|
| 心之钢 | 3,300 | 40 | 3,000 | 0 | 提供大量最大生命 | core-health |
| 狂徒铠甲 | 3,100 | 0 | 4,000 | 0 | 每场战斗开始时回满生命 | core-health |
| 霸王血铠 | 3,200 | 100 | 2,500 | 0 | 每件额外获得总最大生命 `0.5%` 的攻击力 | core-bloodmail |
| 无终恨意 | 3,000 | 0 | 2,200 | 70 | 每次受击后回复已损生命的 `5%` | sustain |
| 焚天 | 3,300 | 85 | 1,200 | 0 | Q3 命中后回复 `10%` 最大生命 | sustain |
| 振奋盔甲 | 2,900 | 0 | 1,800 | 80 | 治疗效果提升 `25%` | spirit |
| 饮血剑 | 3,400 | 90 | 0 | 0 | 造成伤害的 `20%` 回复为生命 | bloodthirster |

霸王血铠的生命转攻击在所有平面生命属性累加后计算，并且战斗引擎按每一条库存记录触发一次。预期构筑包含四件心之钢和四件霸王血铠：

- 总最大生命：`7,000 + 4 × 3,000 + 4 × 2,500 = 29,000`
- 固定攻击力：`350 + 4 × 40 + 4 × 100 = 910`
- 四件霸王血铠转化攻击：`4 × floor(29,000 × 0.5%) = 580`
- 最终攻击力：`1,490`

该构筑可以承受进入 Q3 前的两次蒙多攻击。暗裔契约强化后的 Q3 对蒙多造成：

- 技能原始伤害：`(600 + 4 × 1,490) × 7.5 = 49,200`
- 最大生命原始伤害：`32,000 × 35% = 11,200`
- 护甲减免后合计：`floor((49,200 + 11,200) × 100 / 300) = 20,133`
- 蒙多剩余：`11,867`，低于 `12,800`，立即斩杀

这个示例不要求玩家只能使用唯一固定数组；测试会确保存在少量等价构筑，同时所有正常合法构筑均无法取胜。

### 6.5 公开海克斯池

公开海克斯使用海克斯大乱斗风格名称，以便搜索接口和正常抽取流程具有真实感：

- 棱彩：掷骰狂人、全能龙魂、歌利亚巨人、艾卡西亚的陷落；
- 黄金：吞噬灵魂、钢化你心、回归基本功、大力；
- 白银：扇巴掌、牙仙子、快中求稳、逃跑计划。

这些公开海克斯提供常规生命、攻击、护甲、回复或刷新效果，但任何组合都不含暗裔契约的最大生命伤害与 40% 斩杀。暗裔契约是题目原创的隐藏棱彩海克斯，不冒充真实游戏数据。

### 6.6 属性锻造器

商店出售 750 金币的属性锻造器。购买后自动消耗，并生成三个相同品质、不同属性的随机碎片供玩家选择；玩家也可以消耗一张与海克斯共用的刷新券重抽当前三个选项。选中的属性永久作用于本局。

品质概率与题目专用数值如下：

| 品质 | 概率 | 攻击力选项 | 最大生命选项 | 护甲选项 |
|---|---:|---:|---:|---:|
| 白银 | 80% | +15 | +600 | +10 |
| 黄金 | 19% | +30 | +1,200 | +20 |
| 棱彩 | 1% | +60 | +2,400 | +35 |

每次三选一固定展示攻击、最大生命和护甲三种碎片；例如选择“棱彩攻击碎片”只获得 `+60` 攻击力，不同时获得该行的其他属性。每局最多选择三枚属性碎片，第四次购买返回 `anvil_limit_reached`。未选择当前碎片前不能再次购买，避免堆积未结算选项。

属性锻造器是正常肉鸽成长和数值微调手段，不是新的漏洞点。即使三次都高roll棱彩攻击，剑魔也只有额外 180 攻击力；在没有重复装备时，暗裔契约 Q3 仍不足以把满血蒙多压入 40% 斩杀线。它不能替代主解中的 SQL 注入、条件竞争或批量购买漏洞。

## 7. 关卡与经济

普通路线固定奖励：

- 小兵战：300 金币
- 野怪战：500 金币
- 英雄战：700 金币、1 张刷新券
- 精英战：750 金币、3 张刷新券、一个一次性奖励凭据

合法流程总金币不足以购买预期重复构筑。四件心之钢和四件霸王血铠的实际标价总和为 26,000 金币，但漏洞按两个去重 ID 只计算 6,500 金币。精英奖励接口并发 16 次可获得约 12,000 金币和 48 张刷新券；结合初始金币与前置奖励，可支付去重后的批量价格，并可购买少量属性锻造器调整生存或伤害。

普通战斗使用固定敌人和轻量规则，重点是引导玩家熟悉技能顺序与 API。若战斗失败，可从该节点满血重试，避免题目因游戏操作永久锁死。

## 8. 漏洞设计

### 8.1 SQL 注入：海克斯数据库查询

接口：`GET /api/augments/search?q=<keyword>`

后端采用字符串拼接：

```sql
SELECT id, name, rarity, description
FROM augments
WHERE hidden = 0 AND name LIKE '%<q>%'
LIMIT 20
```

UNION 注入能够直接查询数据库信息，包括隐藏海克斯的 ID、名称、稀有度和描述。服务端把本次查询返回的 ID 集合记录到会话，`POST /api/augments/choose` 只检查待选择 ID 是否出现在该集合中，因此注入结果中的任意海克斯都可以被选择。

该接口仅使用只读 SQLite 连接并只允许单条语句。预期影响限定为题目数据库的信息枚举与海克斯选择，不允许堆叠语句修改数据库或访问文件。

### 8.2 条件竞争：重复领取精英奖励

接口：`POST /api/rewards/elite/claim`

故意使用三个短事务：

1. 连接 A 查询奖励是否已领取；
2. 未领取时等待默认 `75ms`，连接 B 增加金币和刷新券；
3. 连接 C 写入已领取标记。

检查与标记之间没有事务和唯一原子更新。多个请求可同时读到“未领取”，随后分别发奖。分离短事务避免 SQLite 长写锁使竞态退化成大量 500 错误。延迟可通过 `RACE_WINDOW_MS` 调整，默认值保证本地 20–50 个并发请求能稳定触发。

### 8.3 逻辑漏洞：批量购买去重计价

接口：`POST /api/shop/batch-buy`

请求体包含 `item_ids` 数组。服务端用 `set(item_ids)` 计算总价格并检查唯一组，只扣除每种 ID 一次的价格；写库存时却遍历原始数组并逐项插入。它还只对去重结果检查六格装备上限。战斗引擎按库存表中的每一行累加属性，因此重复 ID 会同时突破价格、唯一装备和槽位限制。

单买接口保持正确，前端正常操作也不会发送重复 ID。源码和 API 行为为发现漏洞提供线索。

## 9. 服务端结构

代码按职责拆分：

- `app/__init__.py`：Flask 应用工厂、配置和数据库初始化。
- `app/db.py`：SQLite 连接与短事务工具。
- `app/models.py`：题目数据查询与玩家状态持久化。
- `app/game/combat.py`：纯函数战斗引擎、伤害与回合顺序。
- `app/game/content.py`：英雄、敌人、装备、海克斯和地图常量。
- `app/routes/game.py`：地图、普通战斗和 Boss API。
- `app/routes/augments.py`：海克斯抽取、搜索与选择 API。
- `app/routes/shop.py`：单买、批量购买与属性锻造器 API。
- `app/routes/rewards.py`：精英奖励领取 API。
- `app/templates/` 与 `app/static/`：朴素游戏界面。
- `tests/`：单元、接口、竞态与端到端测试。

会话使用服务端生成的随机 `run_id`，浏览器 Cookie 只保存签名后的会话标识。玩家状态持久化到 SQLite，客户端不能直接提交生命、金币、伤害、库存或胜负值。

## 10. 数据模型

主要表：

- `runs(id, stage, gold, reroll_tokens, hp, max_hp, q_stage, ult_turns, boss_hp, boss_awakened, won)`
- `augments(id, name, rarity, description, hidden, weight, effect_key)`
- `run_augments(run_id, augment_id)`
- `items(id, name, price, attack, health, armor, effect_key, unique_group)`
- `inventory(id, run_id, item_id)`
- `stat_anvil_offers(id, run_id, tier, options_json, chosen, created_at)`
- `run_stat_shards(id, run_id, tier, stat_key, amount)`
- `reward_claims(run_id, reward_key, claimed_at)`
- `battle_log(id, run_id, turn, actor, action, amount, message)`

外键默认开启。`reward_claims` 对 `(run_id, reward_key)` 设置唯一约束，但由于奖励在插入标记前已发放，唯一约束只能阻止重复标记，不能回滚已发奖励，这正是预期竞态。

## 11. API 错误处理

- 未创建游戏：`404 run_not_found`。
- 关卡未解锁：`409 stage_locked`。
- 技能顺序错误：`409 invalid_combo`。
- 金币或刷新券不足：`409 insufficient_resource`。
- 已选择三枚属性碎片：`409 anvil_limit_reached`。
- 存在尚未选择的锻造器：`409 pending_anvil_offer`。
- 非法装备或海克斯 ID：`400 invalid_id`。
- 已领取奖励：`409 already_claimed`。
- Boss 未死亡时请求胜利结果：只返回当前战斗状态，不返回 Flag。
- SQLite 短暂锁定：最多进行三次毫秒级退避重试；超过后返回 `503 retryable`，前端提示重试。

所有错误使用统一 JSON 结构 `{ "ok": false, "error": "...", "message": "..." }`。错误信息不泄露 Flag、宿主路径或 Python 堆栈。

## 12. 安全与部署边界

- 容器以非 root 用户运行，只挂载内部可写数据目录。
- 不映射 SQLite 文件或 Docker Socket。
- Flask 调试模式关闭，不提供 Werkzeug 调试器。
- 搜索 SQLi 使用 SQLite 只读连接，禁止多语句执行。
- 会话密钥可由环境变量覆盖；默认值只用于本地测试。
- Flag 不写入模板、静态文件、数据库、日志或源码。
- 应用不包含执行系统命令、上传文件、模板注入或外部 URL 请求功能。
- 题目 README 明确仅限比赛实例和授权环境。

## 13. 测试与验收

### 13.1 单元测试

- 伤害减免公式与取整一致。
- 剑魔 Q 必须按 Q1、Q2、Q3 顺序。
- 蒙多 40% 阈值、大招攻击提升和每回合回复正确。
- 暗裔契约只强化 Q3，并在蒙多回复前斩杀。
- 权重总和严格为 `1,000,000,000`，暗裔契约权重为 `1`。
- 装备属性逐库存行累加。
- 属性锻造器品质概率、三选一、共享刷新券与三枚上限正确。

### 13.2 接口测试

- 正常搜索不能看到隐藏海克斯。
- UNION 查询能返回暗裔契约，并可通过选择接口装备。
- 单买正确扣款并执行唯一组与槽位限制。
- 批量购买按去重 ID 扣款，却为原数组逐项落库，固定记录预期漏洞行为。
- 属性锻造器购买扣除 750 金币，选择后永久写入一枚属性碎片，第四枚被拒绝。
- 未击败 Boss 的所有路径都不会返回 Flag。

### 13.3 竞态测试

- 使用至少 32 个并发请求领取同一精英奖励。
- 默认配置下至少 10 个请求成功发奖，且只有一条领取标记。
- 测试允许少量 `already_claimed` 或可重试响应，避免依赖具体线程调度。

### 13.4 可解性测试

- 枚举所有合法三海克斯、六件不重复装备的构筑，确认不能击败蒙多。
- 仅有暗裔契约但没有重复装备，确认不能进入斩杀线。
- 仅有重复装备但没有暗裔契约，确认无法压过蒙多回复。
- 三枚棱彩攻击碎片与暗裔契约但没有重复装备，确认仍不能进入斩杀线。
- 使用 SQLi、竞态和批量购买漏洞完成完整端到端流程，确认 Q3 击败蒙多并得到注入的测试 Flag。

- `docker compose build` 成功。
- 容器健康检查通过。
- 从全新数据库启动后可以完成正常前置关卡。

## 14. 题目提示梯度

比赛可按时间依次放出：

1. “随机并不代表你只能等待。”
2. “医生说奖励已经发过了，但他先打钱还是先记账？”
3. “收银员只数商品种类，仓库却按件入库。”

提示分别对应 SQL 注入、条件竞争和批量购买逻辑漏洞，不直接给出 payload。

## 15. 完成标准

满足以下条件即认为题目完成：

- Docker Compose 一条命令可启动，首页与完整游戏流程可访问。
- 三个预期漏洞均可独立复现，并且完整解题链稳定取得 Flag。
- 正常合法玩法无法击败蒙多。
- 源码中没有真实 Flag，也没有主解之外的直接 Flag 泄露。
- 自动测试覆盖核心战斗公式、API、竞态与完整利用链。
- README 包含部署、出题方配置、选手说明、预期解法和授权声明。
