# 随机事件节点设计

## 目标

让地图中的事件节点成为一次性、可选择且有明确结算反馈的肉鸽事件，而不是进入后无变化地回到地图。

## 规则

进入事件节点时，后端为该节点持久化生成一组事件卡；同一局刷新页面或重复请求时始终看到同一组。三类事件等概率抽取一类：

1. **战利品箱**：一张卡，获得 900 金币或 1 张刷新券。
2. **血契祭坛**：两张卡，分别是失去当前生命 20%（至少 1）换取 +80 攻击，或失去当前生命 15%（至少 1）换取 +45 护甲。选择不能使 HP 低于 1。
3. **暗裔遗物**：两张无代价卡，分别获得 +1200 最大生命或 +50 攻击。

选择任何一张卡后，事件节点标记为 `closed`，本局 `stage` 回到 `event`；前端显示一次结算文字和“继续路线”按钮。事件不产生海克斯，不改变篝火的唯一海克斯来源规则。

## 数据和接口

新增 SQLite `node_events` 表，字段：`run_id`、`node_id`、`event_key`、`offer_json`、`chosen_key`。`(run_id,node_id)` 唯一。

- `GET /api/events/<node_id>`：仅当前的事件节点可读取；若不存在记录则生成并返回 `offer`。
- `POST /api/events/<node_id>/choose`：仅可选择该记录中未结算的 `choice_key`，原子地写入选择、更新金币/刷新券/属性或 HP、关闭节点；重复选择返回 409。

属性奖励写入现有 `run_stat_shards`，与锻造器相同地参与 `stats()` 计算。前端不计算任何奖励值。

## 前端

当 `run.stage === 'event'` 且当前地图节点类型为 `event` 且状态不是 `closed` 时，显示事件幕。卡片显示事件标题、代价、收益和选择按钮；点击后展示后端返回的结算文案与“继续路线”。其他 `event` 阶段继续使用地图幕。

## 验收与自检

- 同一节点重复读取返回同一候选；不同事件节点可独立生成。
- 选择只能执行一次，节点关闭后地图可继续。
- 金币、刷新券、属性与生命值奖励均由后端正确持久化；HP 不低于 1。
- 事件不写入 `run_augments`。
- 全量 pytest、JavaScript 语法检查、Docker 自动求解器通过。
- 无占位符、无与“海克斯只来自篝火”冲突的奖励来源。
